# OAuth troubleshooting: `unauthorized_client` on Drive token refresh

## What was asked

Issue #87: `homedrive`'s personal Google OAuth client (Cloud project
`313423816598`, configured 2026-09-03) served its initial access token fine,
but the **first token refresh** failed with:

```
couldn't fetch token: unauthorized_client: if you're using your own client id/secret,
make sure they're properly set up following the docs
```

Three questions, in priority order:

1. What actually causes `unauthorized_client` (as distinct from `invalid_grant`)
   on a refresh-token grant for a Google OAuth client used by rclone's Drive
   backend, and how does someone check each documented cause in the Cloud
   Console?
2. What is rclone's own documented procedure for giving its Drive backend a
   personal OAuth client on a headless machine (no browser)?
3. (Lower priority, for issue #86) Can rclone's Drive backend construct an
   `Fs` and refresh tokens without an `rclone.conf` file at all, with
   homedrive supplying credentials and persistence itself?

This file answers all three from primary sources (rclone's own source at the
pinned version, rclone's published docs, and the OAuth 2.0 spec / Google's
own identity docs), and separates what those sources establish from what is
only reported in issue trackers/forums.

**Pinned version confirmed**: `homedrive/go.mod` pins
`github.com/rclone/rclone v1.75.0`. Everything sourced from rclone's own code
below was read directly from that module version in the local Go module
cache (`$(go env GOMODCACHE)/github.com/rclone/rclone@v1.75.0`), not from
`main` or a changelog, so it reflects exactly what's compiled into the
`homedrive` binary today.

## Q1 — What causes `unauthorized_client`, and how does it differ from `invalid_grant`?

### The exact error text is generated by rclone, not by Google, and its source settles the `unauthorized_client` vs `invalid_grant` question directly

The message `homedrive` logged is rclone's own error-wrapping code, not
Google's raw response. Read directly from the pinned version:

`lib/oauthutil/oauthutil.go`, function `maybeWrapOAuthError` (called from
`TokenSource.Token()` on every refresh attempt):

```go
switch resp.Error {
case "invalid_client", "unauthorized_client", "unsupported_grant_type", "invalid_scope":
        suggestion = "if you're using your own client id/secret, make sure they're properly set up following the docs"
case "invalid_grant":
        fallthrough
default:
        suggestion = fmt.Sprintf("maybe token expired? - try refreshing with \"rclone config reconnect %s:\"", remoteName)
}
newErr = fmt.Errorf("%s: %s", resp.Error, suggestion)
```
(`fs/config/oauthutil` doesn't exist in this tree; the file lives at
`lib/oauthutil/oauthutil.go` in v1.75.0 — see "what changed" note below if
citing a different rclone version.)

This means: **rclone groups `invalid_client`, `unauthorized_client`,
`unsupported_grant_type`, and `invalid_scope` into one bucket** ("your client
id/secret setup is wrong") and treats **`invalid_grant`** as a separate,
different bucket ("the token itself is stale — reconnect"). The literal
string `resp.Error` in our log line — `unauthorized_client` — is Google's raw
`error` field from the token endpoint's JSON error body, decoded verbatim by
this code (`retrieveErrResponse{ Error string \`json:"error"\` }`) and never
rewritten to a different code. **Our production error genuinely is
`unauthorized_client`, exactly as issue #87 states, and rclone did not
mask a different underlying code.**

### `unauthorized_client` and `invalid_grant` are formally different in the OAuth 2.0 spec Google implements

RFC 6749 §5.2, "Error Response" (Access Token Request), defines both codes:

> **invalid_grant**
> The provided authorization grant (e.g., authorization code, resource
> owner credentials) or refresh token is invalid, expired, revoked, does
> not match the redirection URI used in the authorization request, or was
> issued to another client.
>
> **unauthorized_client**
> The authenticated client is not authorized to use this authorization
> grant type.

— [RFC 6749 §5.2](https://www.rfc-editor.org/rfc/rfc6749#section-5.2)

So per spec: `invalid_grant` is about the *token/grant itself* (expired,
revoked, wrong client). `unauthorized_client` is about the *client's
authorization to use the refresh-token grant type at all* — a different
failure axis. This matches how rclone's own code splits them (above) and
confirms issue #87's framing: a refresh token being present and a
`invalid_grant` response absent is meaningful — it means we are not looking
at a revoked/expired token, we are looking at a client-configuration
problem, per both rclone's code and the spec it implements.

### The "Testing"-mode 7-day refresh-token expiry produces `invalid_grant`, NOT `unauthorized_client` — ruled out

Google's own identity docs state:

> A Google Cloud Platform project with an OAuth consent screen configured
> for an external user type and a publishing status of "Testing" is issued
> a refresh token expiring in 7 days.

— [Google Identity: OAuth 2.0 docs](https://developers.google.com/identity/protocols/oauth2)

And when a refresh token stops working for that reason, Google's docs state
the resulting failure surfaces as **`invalid_grant`**, not `unauthorized_client`.

This directly rules out the framing's own candidate hypothesis: **the
7-day Testing-mode refresh token expiry is not a plausible cause of the
`unauthorized_client` error we saw.** If that were the cause, the log line
would read `invalid_grant`, and per issue #87 it does not. This should be
struck from the suspect list, not merely deprioritized.

### Documented, checkable causes of `unauthorized_client` specifically

The OAuth 2.0 spec's definition ("client not authorized for this grant
type") is generic by design — it is the authorization *server's* (Google's)
decision, and neither the spec nor rclone's docs enumerate every server-side
condition that triggers it. What follows is everything I could find that is
either (a) rclone's own documented client setup requirements — which, if not
followed, would plausibly produce exactly this "client not authorized"
response — or (b) explicitly labeled as forum/issue-tracker-reported, not
official.

**Documented (rclone's own instructions for "create your own client_id"),
from [rclone.org/drive/#making-your-own-client-id](https://rclone.org/drive/#making-your-own-client-id):**

| # | Setting | rclone's exact documented instruction | How to check it in Console |
|---|---|---|---|
| 1 | Drive API enabled on the client's project | "Under 'ENABLE APIS AND SERVICES' search for 'Drive', and enable the 'Google Drive API'." | APIs & Services → Enabled APIs → confirm "Google Drive API" is listed for project `313423816598`. |
| 2 | OAuth client **application type** | "Go to Overview on the left panel, click 'Create OAuth client'. Choose an application type of 'Desktop app' and click 'Create'." | APIs & Services → Credentials → the OAuth 2.0 Client ID in use → confirm "Application type: Desktop app". |
| 3 | Consent screen audience | "under Audience select 'External'" (or "Internal" only for Workspace orgs, and only if the Drive account is in that same Workspace) | APIs & Services → OAuth consent screen / Audience → confirm "External" (or "Internal" + same-org Drive account). |
| 4 | Scopes added to the consent screen | Three scopes documented: `https://www.googleapis.com/auth/docs`, `https://www.googleapis.com/auth/drive`, `https://www.googleapis.com/auth/drive.metadata.readonly` | Data Access tab on the consent screen → confirm all three are listed. |
| 5 | Test user added (while in Testing) | "Add yourself as a test user and press save." | Audience tab → Test users → confirm the authorizing Google account is listed. |
| 6 | Publishing status | Either Testing (works, but see the ruled-out 7-day caveat above — that's `invalid_grant`, not our error) or Published/In production (`PUBLISH APP` button) | Audience tab → confirm status, and that the account used was added as a test user if still in Testing. |

None of rows 1–6 is confirmed as *the* cause of our specific
`unauthorized_client` — I could not see the Console for project
`313423816598` and did not verify any of them. They are simply the complete,
documented list of setup steps rclone itself says are required, presented
so someone with Console access can walk through them directly against
issue #87.

**Reported in forums/issue trackers, NOT confirmed by official docs (flagged
explicitly as such — do not treat as diagnosis):**

- **Client with blank `client_id`/`client_secret` in `rclone.conf`, but a
  token that was actually issued against a real client.** rclone issue
  [rclone/rclone#1220](https://github.com/rclone/rclone/issues/1220) (2017,
  rclone v1.34–v1.36, now closed) reproduced exactly the string
  `"error" : "unauthorized_client"` from Google's server, and multiple
  commenters found their `rclone.conf` had empty `client_id`/`client_secret`
  fields for the affected remote — caused, per maintainer `ncw`'s comment,
  by an old config-save race that was reportedly fixed in later versions.
  This is old and reportedly resolved, but the underlying *mechanism* it
  describes — a token minted for a real client being sent with no
  `client_id`/`client_secret`, or a mismatched pair — is a concrete,
  directly checkable thing: **read `client_id` and `client_secret` for the
  `gdrive` section straight out of the live `rclone.conf` on
  `gruissan.local` and confirm both are non-empty and match what's shown for
  the OAuth client in Console.** This is unverified against project
  313423816598 and is presented as a hypothesis worth ruling in or out
  mechanically, not a confirmed diagnosis.
- **A related but textually distinct rclone bug**,
  [rclone/rclone#7825](https://github.com/rclone/rclone/issues/7825) (still
  produces `invalid_client`, not `unauthorized_client` — a different one of
  the four codes in rclone's bucket above): rclone always sends its
  *built-in default* client secret alongside a caller-supplied token/client
  when the backend defines a default id/secret (as `drive` does), and
  ignores attempts to clear that default with an empty override. Flagged
  because it demonstrates the same *class* of bug (client credentials sent
  to Google not matching what the token was actually issued for) can
  produce any of the four codes in rclone's bucket, not specifically because
  it's confirmed to be our case.
- **Google Workspace admin API access controls.** If the Drive account being
  synced is a Google Workspace (not consumer/personal Gmail) account, a
  Workspace admin can mark third-party OAuth clients "Blocked" or "Limited"
  under Admin console → Security → API controls → App access control
  ([support.google.com/a/answer/13152743](https://support.google.com/a/answer/13152743)).
  Google's help text describes this producing "an authorization error" for
  the user; it does **not** state the literal error code, so I cannot
  confirm this produces `unauthorized_client` specifically rather than some
  other rejection. Only relevant at all if the Drive account in question is
  a Workspace account — not established either way for this deployment.

## Q2 — rclone's documented procedure for a personal OAuth client on a headless machine

### Creating the client (rclone's own instructions, quoted in full context)

Source: [rclone.org/drive/#making-your-own-client-id](https://rclone.org/drive/#making-your-own-client-id)
(fetched 2026-09-07; current live page, not versioned per rclone release —
see "what I could not establish" below).

Full documented sequence, quoted:

1. "Log into the Google API Console with your Google account."
2. "Select a project or create a new project."
3. "Under 'ENABLE APIS AND SERVICES' search for 'Drive', and enable the
   'Google Drive API'."
4. "Click 'Credentials' in the left-side panel (not 'Create credentials',
   which opens the wizard)."
5. Configure the OAuth consent screen if not already done: "enter an
   'Application name' ('rclone' is OK); enter 'User Support Email' ...
   under Audience select 'External'."
6. Add scopes: "`https://www.googleapis.com/auth/docs`",
   "`https://www.googleapis.com/auth/drive` in order to be able to edit,
   create and delete files with RClone", and
   "`https://www.googleapis.com/auth/drive.metadata.readonly` which you may
   also want to add."
7. "click Audience. Scroll down and click '+ Add users'. Add yourself as a
   test user and press save."
8. "Go to Overview on the left panel, click 'Create OAuth client'. Choose an
   application type of 'Desktop app' and click 'Create'."
9. "Go to 'Audience' and then click 'PUBLISH APP' button and confirm." (If
   External; skippable for Internal/Workspace-only clients.)
10. "Provide the noted client ID and client secret to rclone."
11. "Run the web-based authorization flow from within rclone config, by
    answering 'Y' when it asks 'Token already configured - replace it?'."

On Testing vs Production, rclone's page is explicit and directly relevant
to the ruled-out hypothesis above: "Keeping the application in 'Testing'
will work as well, but the limitation is that any grants will expire after a
week... So for typical personal rclone use you can leave the app unverified,
accept the warning screen, and publish it (rather than leaving it in
'Testing') to avoid the weekly grant expiry."

### How the *initial* authorization is obtained with no browser on the target machine

Confirmed against `cmd/authorize/authorize.go` and
`lib/oauthutil/oauthutil.go` in the pinned v1.75.0 source, and against
[rclone.org/remote_setup/](https://rclone.org/remote_setup/):

1. On the **headless machine**, run `rclone config` (or `rclone config
   reconnect <remote>:` if the remote already exists) and answer **N** to
   "Use web browser to automatically authenticate rclone with remote?" —
   this is the literal prompt text in v1.75.0
   (`lib/oauthutil/oauthutil.go`, state `*oauth-confirm`):
   > "Use web browser to automatically authenticate rclone with remote? \*
   > Say Y if the machine running rclone has a web browser you can use \*
   > Say N if running rclone on a (remote) machine without web browser
   > access"
2. rclone then prints the exact command to run on the machine that *does*
   have a browser (source: state `*oauth-remote` in the same file):
   ```
   rclone authorize "drive" "<base64_json_blob_of_overridden_options>"
   ```
   (the blob argument is only included if any config options were
   overridden from defaults — e.g. a custom `client_id`/`client_secret`;
   for a bare default remote it prints just `rclone authorize "drive"`).
3. On the **machine with a browser**, run that exact command. It is
   registered as `cmd/authorize/authorize.go`:
   ```
   rclone authorize <backendname> [base64_json_blob | client_id client_secret]
   ```
   "Use as instructed by rclone config." This opens a browser (or prints a
   URL, with `--auth-no-open-browser`), runs a **local loopback webserver**
   to catch the redirect, completes the Google consent flow, and prints a
   result blob.
4. Paste that result blob back into the headless machine's `rclone config`
   prompt (state `*oauth-authorize` — "Then paste the result.").

This matches the framing's expectation exactly: `rclone authorize` on a
second machine with a browser, then transfer the token back. I found no
alternative headless-only flow (e.g. a device-code/TV-and-limited-input-device
grant) implemented for the Drive backend in this version — see the caveat
below on that point.

**A specific correction to the framing's "OOB flow" assumption**: rclone's
Drive backend does **not** use Google's deprecated out-of-band
(`urn:ietf:wg:oauth:2.0:oob`) copy/paste flow. In v1.75.0,
`backend/drive/drive.go`'s `driveConfig.RedirectURL` is set to
`oauthutil.RedirectURL` (`"http://127.0.0.1:<port>/"`, a loopback-interface
redirect per RFC 8252), not `oauthutil.TitleBarRedirectURL` (the OOB
sentinel). The "paste the result back" step in `rclone authorize`'s output
is rclone's **own** blob-transfer mechanism between two rclone processes —
it happens *after* the browser-machine's local loopback webserver has
already completed a normal, still-supported OAuth exchange directly with
Google. Google's own docs confirm the OOB method itself "is no longer
supported" for new clients
([developers.google.com/identity/protocols/oauth2/native-app](https://developers.google.com/identity/protocols/oauth2/native-app)),
but that deprecation does not apply to rclone's Drive flow, because rclone
isn't using it here.

## Q3 — Can rclone's Drive backend run with no `rclone.conf` file at all?

**Yes — this is directly supported by rclone's own config abstraction in the
pinned version, not something that has to be worked around.** This is a
better answer than issue #86 assumed as its default risk case; report it
plainly.

### The mechanism, read from source

`fs/config/config.go` (v1.75.0) defines a small `Storage` interface —
`GetSectionList`, `HasSection`, `DeleteSection`, `GetKeyList`, `GetValue`,
`SetValue`, `DeleteKey`, `Load`, `Save`, `Serialize` — and its package
doc comment says explicitly:

> Storage defines an interface for loading and saving config to persistent
> storage. Rclone provides a default implementation to load and save to a
> config file when this is imported
>
> `import "github.com/rclone/rclone/fs/config/configfile"`
> `configfile.Install()`

The phrasing "when this is imported" is the key fact: **file-backed storage
is opt-in**, not intrinsic to rclone's config system.

Confirmed by the package's own `init()` (`fs/config/config.go`):
```go
func init() {
    ...
    data = newDefaultStorage()
}
```
`newDefaultStorage()` (`fs/config/default_storage.go`) is a **pure in-memory
map-of-maps** (`sections map[string]map[string]string`) whose `Load()` and
`Save()` methods are both explicit no-ops (`return nil`). This is what
backs rclone's config **before any config-file package is imported at
all** — it is rclone's actual default, not a fallback.

`configfile.Install()` (`fs/config/configfile/configfile.go`) does exactly
one thing: `config.SetData(&Storage{})`, swapping in a file-backed
`Storage` implementation. `homedrive`'s own `init()` in
`internal/rcloneclient/rclonefs.go` calls this today — that is what ties
`rclone.conf` in as the source of truth, and it is `homedrive`'s choice, not
a requirement rclone imposes.

`config.SetData` (`fs/config/config.go`) is exported and accepts **any**
type satisfying `Storage`:
```go
func SetData(newData Storage) {
    if configPath == "" {
        return
    }
    data = newData
    dataLoaded = false
}
```
Note the guard: if `configPath` is `""` (the default, or explicitly set via
`config.SetConfigPath("")` — whose doc comment reads "Checks for empty
string, os null device, or special path, all of which indicates in-memory
config"), `SetData` is a no-op and rclone **stays on the in-memory default
Storage** regardless of what's installed. Either path — never installing
`configfile` at all, or installing a homedrive-authored `Storage`
implementation — avoids `rclone.conf` as a file entirely.

### Token refresh persistence goes through this same abstraction, not directly through a file

`lib/oauthutil/oauthutil.go`'s `PutToken` (called by `TokenSource.Token()`
on every successful refresh) writes only through the generic
`configmap.Mapper` interface:
```go
func PutToken(name string, m configmap.Mapper, token *oauth2.Token, newSection bool) error {
    ...
    m.Set(config.ConfigToken, tokenString)
    ...
}
```
Tracing `m.Set` up through `fs.ConfigMap` (`fs/configmap.go`): the Setter
attached to every backend's config map is `setConfigFile(configName)`,
whose `Set` method calls `fs.ConfigFileSet` → wired in `config.go`'s
`init()` to `SetValueAndSave` → `LoadedData().SetValue(...)` +
`SaveConfig()` → `LoadedData().Save()`. **`LoadedData()` returns whatever
`Storage` is currently installed** — the in-memory default, rclone's file
implementation, or a homedrive-authored one. So: **token refresh does not
require a writable file path** — it requires a writable `Storage`, and that
interface is exactly ten small methods that a homedrive-owned
implementation (e.g., backed by the encrypted-loopback secrets file
issue #86 describes) can satisfy directly, without ever going through
rclone's own INI-file code or the `rclone` binary/wizard.

### Constructing the `Fs` itself without a config-file section

`fs.NewFs` → `fs.ParseRemote` (`fs/newfs.go`) supports rclone's
"connection string" syntax, `:type,key=value,key2=value2:path`. When the
remote string starts with `:`, the backend type is taken directly from the
string (`fsName = configName[1:]`) — **no `Storage.GetValue("type", ...)`
lookup against any section is performed at all** in that case. Backend
options supplied inline in the connection string
(`fspath.Parse`'s `connectionStringConfig`) are added to the resulting
`configmap.Map` at `configmap.PriorityNormal`, which is checked *before*
the config-file/Storage getter (`configmap.PriorityConfig`) per the
priority ordering in `fs.ConfigMap`. So a call like
`fs.NewFs(ctx, ":drive,client_id=...,client_secret=...,token=...:")` (or
values supplied via `RCLONE_CONFIG_<name>_<option>` environment variables,
which `fs.ConfigMap` also wires in via `configEnvVars`) can construct a
`*drive.Fs` with **zero pre-existing config-file sections**, in-memory or
otherwise.

### The caveat that keeps this from being completely free

None of this is exposed as a single documented "no config file" mode in
rclone's own docs — I derived it entirely from reading the source, not from
a page that describes this as a supported pattern. Concretely, adopting it
means:

- `homedrive` would need to **write its own `config.Storage`
  implementation** (ten small methods) rather than using
  `fs/config/configfile` — this is new code, not a documented drop-in.
- `homedrive` already imports `github.com/rclone/rclone/fs/config` directly
  today (`internal/rcloneclient/driveapi.go`, for `config.FileGetValue`) —
  separate from `fs/config/configfile`, which is the only one of the two
  named in CLAUDE.md's rclone-import allow-list. Worth flagging since
  removing `configfile` per issue #86 would still leave `fs/config` itself
  in use (as it must, to call `config.SetData`), and that constraint list
  doesn't currently distinguish between the two.
- I did not find, and could not construct from reading further, any
  documented or source-evident way to avoid `fs/config` as a package
  entirely — the `Storage` interface and `SetData` **are** `fs/config`'s
  API surface, so "no rclone.conf file" is achievable, but "zero contact
  with `fs/config`" is not, on this reading.

### What I could not establish for Q3

- **Whether this in-memory/custom-`Storage` path is actually exercised
  anywhere in rclone's own test suite or by any other known caller**, i.e.
  whether it's a maintained, intentionally-supported surface or an
  incidental consequence of the interface's design that could change
  without notice in a future rclone release. I found no rclone changelog
  entry, doc page, or test specifically validating "run rclone as a library
  with a custom `config.Storage` and no file." This is inferred entirely
  from reading v1.75.0's source, not confirmed as an intentionally stable
  contract.
- **Whether any other file path is touched incidentally** by the Drive
  backend outside the `Storage` abstraction (e.g., temp files, cache
  files) when running with no `rclone.conf` — not investigated; out of
  scope for what was asked.
